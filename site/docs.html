Fusion Conductor

Main agent plans and reviews. Sidekick edits. Install, verify, and customize the pattern on OpenCode.

Overview

Fusion Conductor is an opencode plugin, not an app. It implements the Devin Fusion sidekick pattern: a main agent that plans and reviews but cannot edit files, and a cheaper sidekick that executes every change.

The main agent’s file editing is denied at the permission layer. Its only way to change a file is to hand a spec to the sidekick. Frontier intelligence stays on the plan and the review; mechanical work stays cheap.

Built for OpenCode. A one-line npm plugin install with mechanical edit deny, multi-provider models, and the /conductor command. Forked from opencode-fusion.

This page is the short version. The README is the canonical reference — full setup, provider examples, FAQ, and the complete troubleshooting list live there.

How it works

The plugin injects the agent team at startup. One cycle: main explores (via helpers), plans, hands the sidekick a spec, reviews the diff, loops until it passes, then delivers. Suggested models below are the 2026 defaults from the opencode-go profile.

Agent Role Required Suggested model (2026)
build Main: plan, delegate, review Core opencode-go/kimi-k3
plan Plan mode — same brain, no execute Core opencode-go/kimi-k3
sidekick Execute edits and commands Core opencode-go/deepseek-v4-flash
explore Fast read-only search (built-in agent, model-only) Core opencode-go/deepseek-v4-flash
research Read-only web / docs research Optional opencode-go/deepseek-v4-pro
design Frontend / UI implementation Optional opencode-go/qwen3.8-max
reviewer Critique a plan before implementation; audit a diff before commit Optional opencode-go/glm-5.3-flash
vision Transcribe images if main cannot Optional unset by default

Pick main and sidekick from different model families when you can. The main agent’s review of every sidekick diff becomes cross-vendor for free.

Enforced vs. advised

The pattern’s guarantees live in two layers. Knowing which is which answers most “what if the model just ignores the instructions?” questions.

Enforced — the permission layer

OpenCode checks these on every tool call, regardless of what the model reads or intends. The main agent’s edit, grep, glob, and list are denied — denied tools are removed from the model’s tool schema entirely, so there is no edit tool for it to decline to use. Bash is deny-by-default with a short verify/git allowlist, and delegation is bounded by an explicit task allowlist. The executors cannot commit or push — git commit and git push are denied for the sidekick and design agents, the main agent needs per-command approval for both, and force/mirror/delete-ref pushes are denied outright. The conductor_configure and conductor_status tools serve only the build and plan agents. If the main agent “won’t delegate,” the result is visible inaction — never a silent bypass. These are the same permission maps opencode-fusion v1.2.0 injected, ported verbatim.

Advised — the prompt layer

Spec precision, diff-review rigor, cost discipline, and skill usage are instructions in the agent prompts. Skills load at the model’s discretion in OpenCode — nothing can force an agent to read or apply one — which is exactly why no guarantee depends on them. Slacking here costs quality or tokens, never an unauthorized edit.

Auditable

The optional audit option enables a hook that logs the delegation tree and aggregates per-agent token usage per session, and OpenCode’s session DB records every agent’s actual tool calls — “did it really delegate?” and “where did the tokens go?” are checkable from recorded data.

Install OpenCode

Install the plugin with the opencode CLI (recommended), or add it to the plugin array of your opencode config by hand - the global ~/.config/opencode/opencode.json or a project-level opencode.json. No clone, no build step, no skill.

Install

  1. Run the CLI install command below (or add the plugin line to your opencode.json by hand - pick a profile, or omit options to start bare).
  2. Fully quit and restart OpenCode - opencode auto-installs npm plugins via Bun at startup.
  3. Verify with the lint smoke test.
Terminal 
opencode plugin github:JoshuaKimsey/opencode-fusion-conductor -g

The CLI command writes the plugin entry into your config itself and fails with a real error if the install fails. -g targets the global config; drop it for a project-local .opencode/opencode.json. To pin a specific revision, append a commit SHA to the spec (github:JoshuaKimsey/opencode-fusion-conductor#<commit-sha>) - do not pin by this repo's v1.x tags, which are inherited from upstream opencode-fusion and point at old releases.

Or edit the config by hand:

opencode.json 
{ "plugin": [["opencode-fusion-conductor@1.0.0", { "profile": "opencode-go" }]] }

Works on Windows, macOS, and Linux. No skill, no installer; a bare /conductor runs the first-run setup interview in chat. Uninstall by removing the line and restarting.

The /conductor command

The plugin injects a /conductor slash command. On a fresh install (no profile, no model overrides) a bare /conductor runs a first-run setup interview — profile choice, per-role model overrides, optional audit/claude flags — and applies your answers. Once configured, or when you pass arguments, it skips the interview: with no arguments it runs conductor_status, a read-only report of where the plugin entry lives, the effective role-to-model resolution, and any leftover fusion-install hazards. With arguments it calls conductor_configure, which edits the plugin's own options atomically (a rolling backup at opencode.json.conductor-backup):

  • /conductor — status report once configured; the setup interview when unconfigured.
  • /conductor sidekick=opencode-go/deepseek-v4-flash — set per-role model overrides.
  • /conductor profile chatgpt — switch the subscription profile.
  • /conductor audit=true claude=true — toggle the optional feature flags.

After a change, restart OpenCode — the agent registry is materialized at startup on opencode 1.18.x, so model changes require a restart. /conductor always tells you so.

Subscription profiles

On a subscription? Set the profile option — "profile": "opencode-go" — and the plugin fills in a ready-made role-to-model mapping. Authentication stays out-of-band via opencode auth login (or /connect): profiles carry no keys and are never asked about in chat.

Profile Subscription Main / sidekick
opencode-go OpenCode Go Kimi K3 / DeepSeek V4 Flash
opencode-zen OpenCode Zen pay-as-you-go Claude Opus 5 / GPT-5.6 Luna
opencode-zen-free OpenCode Zen free tier Big Pickle / MiMo V2.5 Free
chatgpt ChatGPT Plus or Pro GPT-5.6 Sol / GPT-5.6 Luna

Every pick stays overridable per role via the models option, and model lineups rotate — the README’s profiles section is canonical for the full role tables and caveats.

Verify

Open any project that has some lint errors and ask:

Prompt 
fix the lint errors in this project
  • Main delegates via task; sidekick edits; main runs the project’s own lint or test command (for example npm run lint) itself to verify.
  • Main must not edit files directly — edits and freeform shell are denied at the OpenCode permission layer.
  • An occasional struck-through command with a permission error is expected — bash is deny-by-default, and the agent recovers by reading the file or delegating. A denied command is the guardrail working, not the setup failing.

Customize

All plugin options live in the plugin entry of ~/.config/opencode/opencode.json: profile (the subscription profile), models (per-role overrides as role -> "provider/model-id" for build, plan, sidekick, explore, research, design, reviewer, vision), audit (boolean, off by default), and claude (boolean, off by default — enables the Claude Code bridge tools conductor_claude_status/conductor_claude_review, which require the Claude Pro/Max CLI installed and authenticated).

Edit the entry, then restart OpenCode — the agent registry is materialized at startup, so model changes need a full restart. Or run /conductor with arguments to have conductor_configure edit the options for you atomically, and restart when it tells you to. Keep the sidekick cheaper and faster than main when you can.

The README covers the rest: configuration options and examples, adjusting the main agent’s bash allowlist (keep "*": "deny" first; run one command per call — a chained line is matched segment by segment and one denied segment denies the whole call), and migrating from opencode-fusion (run the old undo fusion to remove the file-based install first).

Migration from fusion

Coming from opencode-fusion (the file-based skill bundle)? Three steps:

  1. Say undo fusion with the old fusion-setup skill — or run its installer's undo — to remove the file-based agents and prompts under ~/.config/opencode/. Leftover files would override the plugin-injected agents field-by-field.
  2. Add the plugin line to opencode.json as in Install.
  3. Restart OpenCode.

Run /conductor with no arguments afterwards — conductor_status checks for leftover fusion files and warns you if any are detected. The audit and claude options fold in what the old fusion-audit and fusion-claude plugins provided.

Troubleshooting

Run /conductor with no arguments first — conductor_status checks the usual suspects in one shot: where the plugin entry lives and its options, the effective role-to-model resolution, and leftover fusion-install hazards. It only reports; it changes nothing.

The plugin did not load / the agents are not injected
The config was not loaded. Fully quit and restart OpenCode — plugins auto-install and the agent registry materializes at startup, not mid-session. Confirm the plugin entry is in the plugin array of the right opencode.json and that the version is pinned correctly.
The plugin loads but nothing changes / no conductor command
On opencode 1.18.x, when a plugin's git or npm install fails at startup, opencode exits normally and logs nothing (even with --log-level DEBUG --print-logs) - it runs with the stock agents, which looks exactly like "the plugin did nothing". Fingerprint: an empty ~/.cache/opencode/packages/<spec>/ directory with no node_modules inside. Check that git is on PATH and github.com is reachable, delete the empty directory, and retry the install. The opencode plugin ... CLI command does not swallow this error, so reinstalling via the CLI surfaces it directly.
Leftover fusion files override the injected agents
File-based agents from a previous opencode-fusion install override the plugin-injected agent config field-by-field. Say undo fusion with the old fusion-setup skill (or run its installer's undo) to remove them, then restart. conductor_status names the offending files.
Model changes don't take effect
The agent registry is materialized at startup on opencode 1.18.x, so a change to models or profile requires a full restart. This is a platform limitation, not a plugin bug.

More cases — sidekick never invoked, model 404/400, a blocked bash command, searches missing gitignored files — are covered in the README, which is the canonical reference.

Limitations

  • No dynamic mid-session routing. Model per role is fixed at startup. Devin’s mid-task model swap needs a closed product runtime and is an explicit non-goal here.
  • Config loads at startup. Any change to config or agent prompts needs a full restart.
  • Loop protection is permission-based. Nested delegation is bounded by the task graph (sidekick may spawn only read-only searchers), not numeric depth caps.

FAQ

What happens when the sidekick can’t satisfy the spec?
The main agent escalates on a ladder: feedback naming the specific miss, then — after two misses — it authors the exact patch itself (file, line range, verbatim code) and hands it over to apply. A verbatim patch needs no judgment, so the loop cannot deadlock; you lose the cost saving on that one task only. If even the dictated patch fails verification, the plan is wrong, not the sidekick — the main agent revises the plan.
What if agents ignore the prompts or never load the skills?
You lose quality, not guarantees — see Enforced vs. advised. Delegation is not a behavior the main agent chooses: its edit and search tools are removed from its tool schema, so handing work to the sidekick is the only path to changing a file. The optional audit hook and OpenCode’s session DB record what every agent actually did.
How is this different from superpowers or other orchestration?
Different layer. Skill libraries like superpowers teach agents how to work — process knowledge the model can still ignore. Conductor configures what agents can do at the permission layer, and adds per-role model routing for cost with cross-vendor review as a side effect. No framework, no code — just a one-line plugin on a normal session. The two compose: superpowers supports OpenCode, so its skills can run inside a Conductor setup.
